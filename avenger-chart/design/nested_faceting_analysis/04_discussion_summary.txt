EXPERT DISCUSSION SUMMARY: NESTED FACETING IN AVENGER-CHART
================================================================================

DISCUSSION INITIATED: Expert panel review of nested faceting stack overflow issue
EXPERT RECOMMENDATION: Lazy Compilation for Nested Facets
STATUS: Ready for implementation

================================================================================
KEY FINDINGS
================================================================================

ROOT CAUSE:
  Data flow mismatch between compile time and evaluation time
  - At compile time: inner facet receives FULL dataset
  - At evaluation time: inner facet receives FILTERED dataset
  - Causes infinite recursion → stack overflow

CURRENT ARCHITECTURE ISSUE:
  Arc<CompiledPlot> created eagerly at plot compile time
  No mechanism to defer compilation until filtered data available
  Inner subplot unaware of parent facet's filtering constraints

================================================================================
RECOMMENDED SOLUTION: LAZY COMPILATION
================================================================================

APPROACH:
  Defer compilation of nested facets until evaluation time
  - At evaluation: filter data FIRST
  - Then compile inner plot with filtered data
  - Then evaluate with consistent data context

KEY PRINCIPLE:
  "Compiled marks should always match the data they were compiled for"

HYBRID ARCHITECTURE:
  Single-Level Facets: Current eager compilation (unchanged, fast)
  Nested Facets: New lazy compilation (solves problem)

INDUSTRY PRECEDENT:
  Vega: Each facet level has own data flow
  D3: Data binding deferred to visualization time
  Observable: Progressive transformation through facet levels

================================================================================
ANSWERS TO KEY QUESTIONS
================================================================================

Q1: What's the best architectural approach?
A:  Lazy compilation of nested facets, deferred until filtered data available
    Matches industry patterns (Vega, D3)

Q2: Pass filtered DataFrame through compilation context?
A:  No. Instead, recompile inner plot with filtered DataFrame as input
    More explicit and cleaner than threading through context

Q3: Add data parameter to evaluation methods?
A:  Not needed. Lazy compilation handles it naturally in evaluate_from_data()

Q4: How maintain consistency across measurement and rendering passes?
A:  By design. Each facet level compiles with exact data it will evaluate
    Pass 1 and Pass 2 guaranteed consistent data

Q5: Precedents in Vega/D3?
A:  Yes. Both support arbitrary nesting via progressive data transformation
    Lazy compilation is standard pattern in visualization systems

================================================================================
RISK MITIGATION STRATEGY
================================================================================

Risk 1: Compilation cost moves to render time
  Mitigation: Parallelize compilation, implement caching, lazy only for nesting

Risk 2: Breaking API changes
  Mitigation: Keep single-level faceting unchanged, new path additive only

Risk 3: Memory overhead
  Mitigation: Only store uncompiled plot when nesting detected (opt-in)

Risk 4: Parallel compilation resource usage
  Mitigation: Bounded thread pool, config option to disable, start sequential

================================================================================
CRITICAL SUCCESS FACTORS

2. Support arbitrary nesting depth (3+ levels)
