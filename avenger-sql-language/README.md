# avenger-sql-language

Editor features of avenger-sql scripts: diagnostics, semantic highlighting, the outline, folding and selection ranges, go to definition, references, rename, hover, completion, signature help, and formatting.

A `Document` parses the text of a file with avenger-sql-syntax and analyzes it with avenger-sql once, in the mode of its `Role`, and each request reads that parse and analysis. A chart script analyzes with `analyze`, and a data script with `analyze_data`, and the catalog of both gives the tables of their files. The requests on a data script's statements of files, the completion of their options, formats, and URIs, the hover of an option or of a table that a statement defines, and the outline, apply to a chart script's own tables of files, `CREATE TEMP EXTERNAL TABLE` and `LOAD DATA ... TEMP TABLE`, too. A module has the requests of its syntax, since avenger-sql analyzes a module where a script imports it. The tables of a script come from an avenger-sql `Catalog`, and its functions from a `Library`.

```rust
use std::sync::Arc;

use avenger_sql::{analysis::Options, catalog::MemoryCatalog, library::Library};
use avenger_sql_language::{Document, Role};
use datafusion::arrow::datatypes::{DataType, Field, Schema};

let schema = Schema::new(vec![Field::new("species", DataType::Utf8, true)]);
let catalog = MemoryCatalog::new().with_schema(&["penguins"], Arc::new(schema));
let text = "FROM penguins |> WHERE ";
let document = Document::new(
    text,
    Role::Script,
    Arc::new(catalog),
    Arc::new(Library::new()),
    Options::default(),
);
for item in document.completions((text.len() as u32).into()).items {
    println!("{} {:?} {:?}", item.label, item.kind, item.detail);
}
```

## The requests

Each request of a `Document` reads its file alone. A `Project` answers the requests that cross files, by the path of the file and an offset in it, and each of its results names the file that it is in. The other requests of a project's file are those of its `document(path)`.

| Request | Result | In a `Project` |
|---|---|---|
| `diagnostics()` | The errors of the syntax and of the analysis, with their help and the fixes of the syntax's errors, and the Typst syntax errors of the strings of Typst markup, which fail a chart's render, with the source `Typst`. An error of the analysis inside a statement with an error of the syntax is left out, since it repeats the syntax's, and so is an error that comes from a schema that the catalog doesn't know: at the URIs of files whose table the catalog doesn't give, in a data script or a chart script, and in a statement that reads a table that the catalog defines without a schema. | `diagnostics(path)`: the document's, and the project's at the spans of the data scripts: a name that two data scripts define, at both, a cycle of data scripts, at the read in each, a read of a table whose data script has errors or whose files have no table, which names the script, a warning at a URI outside the project's root, of a data script or a chart script, and the errors of the host's loader. |
| `highlights()` | The classes of the tokens, which the analysis refines: a variable, a range variable, a column, a function by what it computes, and a value of a set. In the options of files, of a data script or of a chart script's own tables of files, the value of `format` is a `Format` and a URI of `uris` a `Uri`, so that a theme can show a format as a constant and a URI as a path. A string of Typst markup, an argument of a parameter that takes markup, such as `title => '#emph[Mass]'`, unless its title sets `syntax => 'plain'`, is parsed with typst-syntax, as avenger-typst-label parses it to render, and its range splits: each range that Typst classes, such as a function or a math operator, is a `Typst` range of that class, and the quotes and the text between stay a string. | |

## Projects

A `Project` holds a document for each file of a project, by its path and its `FileRole`: a data script, a chart script, or a module with the path that `IMPORT MODULE` names it by. It holds the dependency graph of the data scripts, avenger-sql's `Graph`, and analyzes each data script in the graph's order against a `ProjectCatalog` of the host's tables, the definitions of the data scripts before it, the tables of the files that the host gives, and the modules. A data script in a cycle analyzes after the others. Each chart script analyzes against the tables of every data script.

A project does no I/O, as a document does none. The host gives it the texts of the files, the table of each set of files that the data scripts and the chart scripts' own tables of files read, from its loader, keyed by avenger-sql's `Files`, the paths of the project's files, and the errors of its loader with `set_loader_diagnostics`. A set of files without a table has an unknown schema: the statement that reads it has no error at its URIs until the host gives the table. A table that a data script defines is unavailable when the script would not load, as the host's loader finds it: when it has errors, defines a name that another data script defines too, is in a cycle or reads one, or reads a script that would not load. A table without a schema, since its statement has errors or its files have none, is unavailable too, and a statement of another script that reads it has no errors of the analysis, which it can't check without the table's schema. A read of an unavailable table has the project's error, which names the data script and says why: that its files could not be read, or that the project has not read them, or else that the script failed to load, did not load since the scripts that it reads did not, or can't run in its cycle. A name that several data scripts define has one error at each definition, which names every one. Table names compare as the catalog's `default_schema` tells, so `t` and `public.t` name one table when the default schema is `public`.

A module's **member** is a `CREATE PUBLIC` function or constant of its file, which a script, a cell, or another module reaches by a qualified name after it imports the module: the import's alias, or the last name of the module's path without one, then the member's name, as `weather.warm`. One resolution in the project gives each request: `definition`, `references`, and `rename` take a member before a document's own names, and `hover(path, offset)`, `signature_help(path, offset)`, and `completions(path, offset)` give a member's header, its module and its leading comment, its parameters, and after a qualifier and `.`, its module's public members, and otherwise what the file's document gives. A qualified name in an expression whose qualifier the analysis reads as a column or a range variable is that, not a member, and a `PRIVATE` member, which only its module reads, takes none of them. A module's document has no analysis, so a member's uses in its module are the calls and the names of its name there that the analysis doesn't read as columns or variables.

`add`, `set_texts`, and `remove` analyze the files and their dependents again: for a data script, the data scripts downstream of it in the graph before the edit and after it, including the scripts whose imported modules read its tables, the data scripts that define a name that one of these also defines, and the chart scripts that read a table that one of these defines, or that import a module. For a module, they are the scripts that import it and their dependents. `set_texts` changes several files together, as the edits of a rename do, and the other files take the catalog after the change, so that they complete its tables. `set_file_tables` analyzes every data script again, and every chart script with its own tables of files. A chart script's own tables are `TEMP` tables of the chart, so no other file reads, completes, or renames them. `set_paths` and `set_loader_diagnostics` analyze nothing, and the loader's errors take the source `Loader`. An edit leaves out the loader's errors of its file until the host sets them again, and `diagnostics` leaves out a loader's error that the project finds itself. Each of `add`, `set_texts`, `remove`, and `set_file_tables` returns the paths of the files that it analyzed again or removed, so that a host, such as a language server, publishes the diagnostics of those files alone.

A URI is relative to the project's root. A URI outside the root has a warning, since another machine would not have its files: an absolute path, of Unix or of Windows, a `file:` URL, or a relative path whose `..` names go above the root, as `data/../../sales.csv` or `data\..\..\sales.csv`, since `/` and `\` both separate the names of a path.

A `Document` is `Send` and `Sync`, and so is a `Project`. Every edit of the text makes a new `Document`. `analysis()` gives the analysis of a chart script to a host that runs it, and `data_analysis()` the tables, views, and schemas that a data script defines.

A document does no I/O. A host gives it the paths of the project's files with `with_paths`, relative to the project's root and separated by `/`, as `data/files/sales.csv`. Completion in a URI offers the paths that extend the value of the string before the cursor by one segment, the directories ending with `/`, and inserts each with the escapes that the string needs. The files that a directory of the statement's format and compression reads come first, as `.csv` for CSV and `.csv.gz` for CSV with `GZIP`, and the other files after them, since a URI of one file reads it whatever its name.

`quote(name)` writes a name as a script writes it, as completion inserts it: as it is when it is a plain name, and in backticks otherwise, or when it is a reserved word, such as `` `unit price` `` or `` `order` ``. Names are case-insensitive, so `PetalLengthCm` stays as it is.

## Completion

Completion offers what the grammar takes at the cursor, as avenger-sql-syntax's `expected_at` gives it, filled with the names that the analysis and the catalog know there. The analysis's place at the cursor decides the names and functions: a `WHERE` takes the columns of its input and scalar and window functions, an item of `|> AGGREGATE` takes aggregates and marks but no column by itself, `LIMIT` takes no column, and the functions of `MATCH_RECOGNIZE` stand only in its clauses, by the same rules that the analysis reports as errors. After a named argument, an argument takes only the name of a parameter. A subquery takes the columns and the range variables of the queries that it can read, after its own. Columns of the type that the place expects, such as `BOOL` in a `WHERE`, come first. At the start of an argument, the constructors that its parameter takes come first, under the names that the parameter gives them: the constructor named after the argument, then those one level down, as `scale`, `type`, and `pin` after `scale => `, then the values of the parameter's set, before the other items, and in a string, every value of the set.

`tests/completion_eval.rs` evaluates completion at several locations of each of its example queries, in each whole query and in its text cut at the cursor, against an oracle that parses and analyzes each item after the text before the cursor. It fails when completion does not offer the token of the query where the text before the cursor tells it, or offers an item that the oracle rejects. An ignored test, which `--ignored` runs, also tries each keyword, function, and name in the cut text, and fails when completion leaves out an item that the oracle accepts. The evaluation reads chart scripts: its oracle analyzes each text with a catalog of tables and no files, in which a statement of a data script that reads files has an error, so `tests/data_script.rs` tests the completion of data scripts.

## Positions

Positions and ranges are byte offsets of the text, as in avenger-sql-syntax. A host converts them to its own units: the Language Server Protocol takes UTF-16 positions, or UTF-8 positions with a client that offers them, and a text widget can take characters. A request takes an offset at a character boundary, and an offset past the end reads as the end.

## Known gaps

- The crate has no server of the Language Server Protocol.
- A module's document has no analysis, so it has the requests of its syntax alone.
- The text of a module isn't in a script's document: a module's functions have no definition, and completion offers no module paths and no functions of a module. A `Project` gives a qualified name of a module's member its definition, hover, signature help, completion, references, and rename, and `IMPORT MODULE` the module's file as its definition.
- A project renames tables, not schemas. A URI that matches no file has its error from the host's loader, not from the project.
- The analysis records no use of a temporary function's parameters in its body, of a named window, or of a field after a pattern variable, as `s` in `p.s`. These names have no definition, references, rename, or hover. Completion offers the parameters of a function in its body.
- A table that a script defines, a data script's or a chart script's own table of files, has no definition, references, or rename in its document alone. A `Project` gives them.
- Every edit analyzes the whole script again.
